# MÓDULO 06 — TERMINAL, SHELL, PROCESSOS E EXECUÇÃO DE COMANDOS NO AI DEVELOPMENT HARNESS

## 1. MISSÃO PRINCIPAL

Implemente no nosso AI Development Harness um sistema completo de execução de comandos e gerenciamento de processos, permitindo que o agente de IA utilize terminais reais, execute ferramentas de desenvolvimento, acompanhe processos longos, leia resultados, identifique falhas e continue tarefas de programação de forma estruturada.

Este módulo deve funcionar integrado aos módulos anteriores:

- **Módulo 01:** Agent Core e ciclo de execução do agente.
- **Módulo 02:** subagents e orquestração.
- **Módulo 03:** skills, comandos personalizados e hooks.
- **Módulo 04:** Computer Use e automação desktop.
- **Módulo 05:** Browser Automation.
- **Módulo 06:** terminal, shell, execução de processos e sessões de terminal.

O objetivo é que o agente consiga realizar tarefas reais de desenvolvimento, como:

1. Abrir um projeto existente.
2. Identificar a tecnologia utilizada.
3. Verificar as dependências instaladas.
4. Executar comandos de instalação.
5. Iniciar um servidor de desenvolvimento.
6. Manter o servidor em execução enquanto trabalha em outras tarefas.
7. Ler logs e identificar erros.
8. Executar testes.
9. Corrigir problemas.
10. Reiniciar os processos necessários.
11. Verificar se a aplicação está funcionando.
12. Informar o resultado real da execução.

O sistema deve ser compatível com os ambientes disponíveis no Windows, incluindo PowerShell, CMD e WSL, quando instalados. Outros shells podem ser adicionados por configuração.

**Não implemente apenas uma função que executa um comando e devolve o texto de saída.** Implemente um sistema de execução de processos com sessões persistentes, controle de ciclo de vida, streaming, cancelamento, gerenciamento de saída, recuperação e integração com o agente central.

## 2. REGRAS OBRIGATÓRIAS

Antes de modificar o código:

1. Inspecione a estrutura atual do harness.
2. Identifique sua linguagem, seu framework e sua arquitetura.
3. Examine o registro de ferramentas do Agent Core.
4. Verifique como o sistema armazena sessões e tarefas.
5. Identifique qualquer implementação existente de terminal ou execução de processos.
6. Examine como a interface atual apresenta resultados e progresso.
7. Execute os testes existentes.
8. Preserve as funcionalidades que já funcionam.

Depois, clone os repositórios listados neste documento e examine o código-fonte.

Para cada repositório:

- Analise a implementação real.
- Identifique os componentes reutilizáveis.
- Compare as soluções com as existentes no harness.
- Reutilize ou adapte os componentes que trouxerem melhorias concretas.
- Implemente as funcionalidades ausentes.
- Evite sistemas duplicados.
- Respeite as licenças.
- Execute os testes relevantes.
- Documente o que foi efetivamente aproveitado.

Não entregue apenas um plano de arquitetura. Implemente o módulo dentro do projeto existente.

Não reescreva o Agent Core nem crie um sistema independente de ferramentas para contornar os contratos já implementados.

## 4. ARQUITETURA DO MÓDULO

Implemente os componentes abaixo ou amplie os equivalentes já existentes.

### 4.1. Process Execution Service

Serviço central para iniciar e gerenciar processos.

Responsabilidades:

- Receber uma solicitação de execução.
- Validar os parâmetros.
- Selecionar o ambiente de execução.
- Iniciar o processo.
- Capturar stdout e stderr.
- Monitorar o estado.
- Registrar o código de saída.
- Detectar falhas de inicialização.
- Aplicar timeouts.
- Permitir cancelamento.
- Gerenciar o encerramento.
- Retornar resultados estruturados.

O serviço deve ser independente do provedor de IA.

### 4.2. Shell Adapter Registry

Registro dos adaptadores de shell disponíveis.

Implemente adaptadores conforme os ambientes realmente suportados:

- PowerShell.
- CMD.
- WSL.
- Bash.
- Outros shells configurados pelo usuário.

Cada adaptador deve informar:

- Identificador.
- Executável.
- Argumentos de inicialização.
- Diretório padrão.
- Variáveis de ambiente aplicáveis.
- Capacidades.
- Particularidades de quoting.
- Estratégia de encerramento.
- Requisitos de instalação.

Não presuma que todos os shells utilizam a mesma sintaxe de comandos ou as mesmas regras de expansão de argumentos.

### 4.3. Terminal Session Manager

Gerenciador de sessões persistentes de terminal.

Deve permitir:

- Criar uma sessão.
- Identificar a sessão.
- Listar sessões.
- Consultar o estado.
- Enviar entrada.
- Receber saída.
- Redimensionar o terminal.
- Interromper a execução atual.
- Encerrar a sessão.
- Detectar processos encerrados.
- Recuperar informações após falhas.
- Reutilizar uma sessão quando apropriado.

Cada sessão deve ter um identificador estável dentro do contexto do harness.

Diferencie uma sessão interativa de terminal de uma execução pontual de comando.

### 4.4. PTY Manager

Quando a tecnologia escolhida oferecer suporte a pseudoterminais, implemente um gerenciador de PTY.

Deve suportar:

- Inicialização de shells interativos.
- Entrada e saída em tempo real.
- Redimensionamento.
- Sequências ANSI.
- Controle de encerramento.
- Gerenciamento de buffers.
- Tratamento de desconexões.

Não utilize pseudoterminal quando uma execução simples de processo for mais apropriada.

### 4.5. Output Stream Manager

Gerencie as saídas dos processos.

Implemente:

- Captura de stdout.
- Captura de stderr.
- Streaming de saída.
- Identificação da origem dos dados.
- Bufferização.
- Limites de memória.
- Scrollback.
- Paginação de resultados.
- Detecção de encerramento.
- Tratamento de saída incompleta.
- Cancelamento de consumidores.

Não acumule indefinidamente toda a saída de processos longos na memória.

Permita consultar os trechos recentes e recuperar resultados anteriores por meio do mecanismo de persistência, quando apropriado.

### 4.6. Process Registry

Mantenha um registro dos processos iniciados pelo harness.

Cada registro deve conter, quando aplicável:

- ID do processo no harness.
- PID do sistema operacional.
- Sessão de terminal associada.
- Tarefa responsável.
- Comando ou executável.
- Argumentos não sensíveis.
- Diretório de trabalho.
- Horário de início.
- Estado atual.
- Código de saída.
- Última atividade.
- Resultado de encerramento.

Não confunda o PID do sistema operacional com o identificador interno do processo.

### 4.7. Process Lifecycle Manager

Responsável por controlar o ciclo de vida dos processos.

Estados sugeridos:

- `created`
- `starting`
- `running`
- `waiting_for_input`
- `stopping`
- `completed`
- `failed`
- `cancelled`
- `unknown`

Adapte os estados ao modelo já existente no Agent Core.

O sistema deve distinguir processos que estão em execução, aguardando entrada, encerrados ou cujo estado não pode ser determinado.

### 4.8. Command Result Analyzer

Componente para estruturar os resultados das execuções.

Deve identificar:

- Código de saída.
- Mensagens de erro.
- Falhas de inicialização.
- Timeouts.
- Encerramento solicitado.
- Sinais ou códigos de interrupção, quando disponíveis.
- Indícios de compilação malsucedida.
- Resultados de testes.
- Avisos relevantes.

A análise pode utilizar regras determinísticas e, quando necessário, o Agent Core.

Não classifique toda saída escrita em stderr como falha. Alguns programas utilizam stderr para avisos e mensagens informativas.

## 6. EXECUÇÃO DE COMANDOS

### 6.1. Execução pontual

Permita iniciar um processo, aguardar sua conclusão e retornar o resultado.

O resultado deve incluir:

- Status.
- Código de saída, quando disponível.
- Saída padrão.
- Saída de erro.
- Duração.
- Identificador da execução.
- Indicação de timeout ou cancelamento.
- Diagnóstico de falhas de inicialização.

Para comandos longos, ofereça uma execução assíncrona e um mecanismo para consultar os resultados posteriormente.

### 6.2. Execução interativa

Permita que o agente mantenha uma sessão de terminal aberta.

Exemplos:

- Servidor de desenvolvimento.
- Shell interativo.
- REPL.
- Ferramenta que solicita entrada.
- Processo que apresenta resultados progressivamente.

O agente deve conseguir enviar entrada, receber saída e continuar trabalhando sem precisar reiniciar o processo.

### 6.3. Processos persistentes

Implemente suporte a processos que devam continuar em execução enquanto outras tarefas acontecem.

Exemplos:

- Servidor web.
- Metro bundler.
- Expo development server.
- Vite.
- Next.js.
- Watchers.
- Compiladores em modo de observação.
- Serviços locais.

O harness deve conseguir identificar que o processo continua ativo, consultar os logs e encerrá-lo explicitamente quando necessário.

Não considere que um processo falhou apenas porque não produziu saída durante um curto intervalo.

### 6.4. Execução de comandos encadeados

Permita executar sequências de comandos quando apropriado.

O sistema deve distinguir:

- Comandos independentes.
- Comandos dependentes.
- Execução sequencial.
- Execução paralela.
- Pipelines.
- Scripts.
- Sessões interativas.

Não concatene automaticamente entradas fornecidas pelo modelo em strings de shell sem considerar as regras de quoting e os riscos de interpretação.

Sempre que possível, utilize a execução estruturada de um executável com uma lista de argumentos.

Quando a tarefa realmente exigir sintaxe de shell, utilize o adaptador do shell correspondente.

### 6.5. Diretório de trabalho

Permita definir o diretório de trabalho por execução ou sessão.

O sistema deve:

- Validar o caminho.
- Identificar diretórios inexistentes.
- Respeitar o workspace selecionado.
- Preservar o diretório atual de uma sessão interativa.
- Evitar misturar diretórios de projetos diferentes.
- Informar claramente o diretório utilizado.

Não altere o diretório global do aplicativo para executar uma tarefa específica.

### 6.6. Variáveis de ambiente

Permita configurar variáveis de ambiente por processo ou sessão.

Implemente:

- Herança controlada.
- Sobrescrita explícita.
- Remoção de variáveis quando necessário.
- Validação dos nomes.
- Separação entre configurações do usuário e do projeto.
- Proteção de valores sensíveis.
- Evitar exposição de segredos nos logs.

Não copie automaticamente todas as variáveis de ambiente para o contexto do modelo.

Quando o agente precisar consultar informações do ambiente, forneça somente os dados relevantes à tarefa.

## 7. CANCELAMENTO, TIMEOUT E RECUPERAÇÃO

### 7.1. Timeouts

Implemente timeouts configuráveis para:

- Inicialização.
- Execução pontual.
- Espera por saída.
- Espera por encerramento.
- Entrada interativa.
- Encerramento de processo.

Um timeout de espera por saída não deve necessariamente encerrar o processo. Diferencie o tempo limite de observação do limite total de execução.

### 7.2. Cancelamento

Permita que o usuário ou o Agent Core cancele uma tarefa.

O cancelamento deve:

1. Identificar a execução ou sessão.
2. Solicitar a interrupção apropriada.
3. Aguardar o resultado do encerramento.
4. Registrar o estado final.
5. Liberar os recursos.
6. Informar se o processo foi efetivamente encerrado.

### 7.3. Encerramento no Windows

Implemente o encerramento de processos considerando as particularidades do Windows.

Quando necessário, utilize mecanismos apropriados para grupos de processos, árvores de processos ou Job Objects.

Não presuma que encerrar o processo pai encerrará automaticamente todos os processos filhos.

Evite encerrar processos que não foram iniciados ou autorizados pelo harness.

### 7.4. Recuperação

Quando uma execução falhar:

- Classifique o erro.
- Preserve as informações relevantes.
- Verifique se o processo ainda está ativo.
- Identifique se a sessão continua utilizável.
- Permita nova tentativa quando apropriado.
- Evite repetir automaticamente comandos com efeitos externos importantes.
- Informe o Agent Core sobre o resultado.

Não execute indefinidamente o mesmo comando sem uma estratégia de recuperação.

## 8. INTEGRAÇÃO COM O AGENT CORE

O Agent Core deve utilizar o terminal por meio do registro central de ferramentas.

Implemente integração para:

- Seleção do shell.
- Execução de comandos.
- Recebimento de saída.
- Monitoramento de processos.
- Consulta de resultados.
- Interrupção de tarefas.
- Recuperação de erros.
- Planejamento de comandos subsequentes.
- Registro dos resultados no histórico da tarefa.

O agente deve compreender a diferença entre:

- Comando concluído com sucesso.
- Comando concluído com falha.
- Processo ainda em execução.
- Processo aguardando entrada.
- Execução cancelada.
- Execução cujo resultado não foi confirmado.

Não marque uma tarefa como concluída enquanto os processos necessários ainda estiverem executando, a menos que a própria tarefa exija deixar esses processos ativos.

Não crie um segundo ciclo de agente para controlar o terminal.

Exemplos:

- Agente de backend executa testes de API.
- Agente de frontend inicia o servidor de desenvolvimento.
- Agente de testes executa a suíte automatizada.
- Agente de debugging consulta logs.
- Agente de infraestrutura verifica dependências.
- Agente de documentação executa ferramentas de geração de documentação.

Implemente:

- Identificação do agente responsável.
- Associação entre processo e tarefa.
- Isolamento de sessões quando necessário.
- Limites de concorrência.
- Controle de processos compartilhados.
- Cancelamento.
- Entrega de resultados estruturados ao orquestrador.

Dois agentes não devem encerrar, reiniciar ou alterar simultaneamente um processo compartilhado sem coordenação.

Evite iniciar servidores duplicados para o mesmo projeto sem necessidade.

- Scrollback configurável.

- Paginação.

- Limites de tamanho.

- Últimas linhas.
- Linhas próximas a um erro.
- Trechos que correspondam a um padrão.
- Resumo de uma saída longa.
- Informações estruturadas de testes.

## 14. SEGURANÇA E CONTROLE DE EXECUÇÃO

O terminal concede acesso a capacidades importantes do sistema operacional. Por isso, as permissões devem ser aplicadas no executor real.

Implemente controles proporcionais à arquitetura:

- Validação de parâmetros.
- Identificação do diretório de trabalho.
- Controle de processos.
- Limites de tempo e recursos.
- Tratamento de argumentos.
- Proteção contra exposição de segredos.
- Registro de operações.
- Cancelamento.
- Isolamento de sessões.
- Política de execução.
- Proteção contra encerramento de processos alheios à tarefa.

Não confie exclusivamente no prompt do modelo para decidir se um comando pode ser executado.

Não interprete automaticamente uma string arbitrária como um comando confiável.

Diferencie execução estruturada de executáveis e execução de sintaxe de shell.

Para comandos que exijam uma política específica de autorização, utilize o mecanismo já existente no harness.

Não transforme o sistema em um executor que ignora todas as regras de autorização existentes.

### 14.1. Processos privilegiados

Não eleve privilégios automaticamente.

Se uma operação exigir privilégios administrativos, informe a necessidade e utilize o fluxo apropriado já existente no sistema.

### 14.2. Segredos

Evite incluir nos logs e nas mensagens do modelo:

- Senhas.
- Tokens.
- Chaves de API.
- Credenciais.
- Variáveis sensíveis.
- Conteúdo privado desnecessário.

Se a saída de um processo contiver dados sensíveis, aplique os mecanismos de proteção disponíveis antes de disponibilizá-la ao modelo ou à interface.

### 14.3. Scripts e projetos externos

Não execute automaticamente scripts de instalação apenas porque foram encontrados em um repositório.

O agente deve distinguir inspeção, preparação e execução.

Quando uma operação puder alterar substancialmente o sistema, aplique as políticas de autorização do harness.
