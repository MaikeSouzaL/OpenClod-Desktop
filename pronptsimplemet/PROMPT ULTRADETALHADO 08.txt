# MÓDULO 08 — GIT INTELIGENTE, DIFF, BRANCHES, WORKTREES E COORDENAÇÃO DE ALTERAÇÕES

## 1. MISSÃO PRINCIPAL

Implemente no nosso AI Development Harness um sistema completo de gerenciamento inteligente de versões e alterações de código, utilizando Git como infraestrutura principal.

O objetivo é permitir que o harness controle as modificações realizadas pelo agente principal e pelos subagents, preserve o trabalho preexistente do usuário, crie ambientes isolados para tarefas paralelas, identifique conflitos e integre alterações de maneira controlada.

O módulo deverá funcionar em conjunto com:

- **Módulo 01:** Agent Core.
- **Módulo 02:** Subagents e Orchestration.
- **Módulo 03:** Skills, Custom Commands e Hooks.
- **Módulo 06:** Terminal, Shell e Execução de Processos.
- **Módulo 07:** Code Intelligence e Manipulação de Repositórios.

Não implemente apenas uma interface para executar comandos Git. Construa uma camada de gerenciamento de versões que compreenda o estado do repositório, acompanhe as alterações de cada tarefa e ajude a coordenar o trabalho de múltiplos agentes.

O harness deverá conseguir:

1. Detectar se um projeto utiliza Git.
2. Identificar o estado atual do repositório.
3. Distinguir arquivos modificados, adicionados, removidos e não rastreados.
4. Examinar diffs e alterações por arquivo.
5. Criar branches para tarefas específicas.
6. Criar worktrees isoladas para subagents.
7. Acompanhar as modificações de cada agente.
8. Detectar conflitos entre tarefas.
9. Validar alterações antes da integração.
10. Realizar commits quando solicitado e autorizado.
11. Integrar alterações compatíveis.
12. Recuperar o estado anterior a uma operação realizada pelo próprio harness, quando possível.
13. Registrar um histórico das operações.
14. Apresentar relatórios claros sobre o que mudou e por quê.

**Princípio central:** nenhuma tarefa automatizada deve apagar ou sobrescrever silenciosamente alterações preexistentes do usuário.

Não presuma a linguagem de programação do harness. Selecione as bibliotecas e integrações de acordo com a arquitetura real do projeto.

## 4. ARQUITETURA DO MÓDULO

Implemente os componentes abaixo ou amplie os equivalentes já existentes.

### 4.1. Repository State Manager

Responsável por identificar o estado real do repositório.

Deve consultar e representar:

- Raiz do repositório.
- Branch atual.
- Commit atual.
- Branches locais.
- Branches remotas conhecidas.
- Arquivos modificados.
- Arquivos adicionados.
- Arquivos removidos.
- Arquivos não rastreados.
- Arquivos ignorados, quando necessários.
- Estado do index.
- Alterações staged e unstaged.
- Estado de merge ou rebase.
- Worktrees existentes.
- Conflitos pendentes.
- Alterações ainda não commitadas.

O resultado deve ser estruturado para consumo pelo Agent Core.

Não utilize apenas uma interpretação simplificada de `git status` quando forem necessárias informações adicionais.

### 4.2. Git Operation Service

Centralize as operações Git em um serviço compartilhado.

Ele deverá implementar ou encapsular:

- Consulta de estado.
- Branches.
- Worktrees.
- Diffs.
- Staging.
- Commits.
- Merge.
- Rebase.
- Cherry-pick.
- Stash.
- Histórico.
- Tags.
- Verificação de conflitos.
- Recuperação de operações.

Cada operação deve ter:

- Identificador.
- Parâmetros validados.
- Estado.
- Resultado.
- Erros tipados.
- Registro de execução.
- Associação com a tarefa que a solicitou.

Não crie executores Git independentes para cada subagent.

### 4.3. Diff Engine

Implemente uma camada para obter, interpretar e apresentar alterações.

Ela deve conseguir produzir:

- Diff do workspace.
- Diff do index.
- Diff de um arquivo.
- Diff entre commits.
- Diff entre branches.
- Diff de uma worktree.
- Resumo das alterações.
- Estatísticas de inserções e remoções.
- Lista de arquivos afetados.
- Trechos relevantes.
- Identificação de arquivos binários.

Preserve as informações originais do diff sempre que necessário.

Não considere que todos os arquivos podem ser representados corretamente como texto.

### 4.4. Patch Manager

Centralize a aplicação de alterações.

O serviço deve:

1. Identificar o arquivo alvo.
2. Verificar o estado atual.
3. Confirmar que o patch corresponde ao conteúdo esperado.
4. Aplicar a alteração.
5. Validar o resultado.
6. Gerar o diff.
7. Registrar a operação.
8. Permitir recuperação quando a operação puder ser revertida com segurança.

Se o conteúdo tiver mudado desde a criação do patch, detecte o conflito em vez de sobrescrever silenciosamente.

Utilize o mecanismo de edição do Módulo 07 sempre que possível.

### 4.5. Branch Manager

Gerencie branches associadas a tarefas.

Implemente:

- Criação de branches.
- Consulta de branches.
- Verificação de existência.
- Troca de branch quando apropriado.
- Renomeação.
- Exclusão condicionada.
- Relação entre branch e tarefa.
- Detecção de branches já utilizadas.
- Verificação de alterações pendentes antes de operações que possam afetá-las.

Não troque automaticamente a branch do workspace principal enquanto outro agente ou o usuário estiver utilizando esse mesmo workspace.

### 4.6. Worktree Manager

Este é um dos componentes mais importantes do módulo.

Implemente gerenciamento de worktrees reais do Git.

Deve permitir:

- Criar uma worktree para uma tarefa.
- Associar uma branch à worktree.
- Registrar o agente responsável.
- Identificar o diretório da worktree.
- Consultar seu estado.
- Listar arquivos modificados.
- Executar testes isoladamente.
- Comparar alterações com a referência apropriada.
- Finalizar a tarefa.
- Integrar o resultado.
- Remover a worktree quando não houver alterações que precisem ser preservadas.

Cada worktree deve ter um registro persistente contendo, quando aplicável:

- ID da tarefa.
- ID do agente.
- Caminho do workspace.
- Branch.
- Commit base.
- Data de criação.
- Estado.
- Processos ativos associados.
- Resultado dos testes.
- Estado de integração.
- Pendências.

Não crie diretórios independentes e os chame de worktrees sem utilizar os mecanismos reais do Git.

### 4.7. Conflict Detector

Implemente mecanismos para identificar conflitos entre tarefas.

Considere:

- Arquivos modificados por mais de um agente.
- Regiões sobrepostas.
- Símbolos compartilhados.
- Arquivos de configuração.
- Dependências entre alterações.
- Mudanças na branch base.
- Diferenças de contexto.
- Alterações incompatíveis em interfaces.

Não confunda dois agentes modificando arquivos diferentes com a ausência absoluta de conflitos. Uma mudança pode afetar semanticamente outro arquivo.

Utilize as informações do Módulo 07 para melhorar a análise de impacto.

### 4.8. Merge Coordinator

Coordene a integração das alterações concluídas.

Deve:

1. Identificar a tarefa concluída.
2. Obter o diff da tarefa.
3. Verificar o estado do workspace de destino.
4. Identificar conflitos conhecidos.
5. Verificar a compatibilidade com a base atual.
6. Executar validações pertinentes.
7. Aplicar a estratégia de integração escolhida.
8. Registrar o resultado.
9. Atualizar o estado da tarefa.
10. Preservar informações suficientes para investigar falhas.

Não integre automaticamente todas as branches apenas porque os agentes informaram que terminaram.

### 4.9. Git Operation Journal

Mantenha um histórico estruturado das operações executadas pelo harness.

Registre:

- Operação.
- Repositório.
- Branch.
- Worktree.
- Tarefa.
- Agente.
- Horário.
- Parâmetros não sensíveis.
- Resultado.
- Erro.
- Referências aos commits.
- Arquivos afetados.

Esse histórico deve ajudar a compreender como o repositório chegou ao estado atual.

Não armazene credenciais, tokens ou segredos desnecessários nos registros.

## 5. GESTÃO INTELIGENTE DE BRANCHES

### 5.1. Estratégia de branches

Permita configurar estratégias como:

- Trabalhar na branch atual.
- Criar uma branch por tarefa.
- Criar uma branch por subagent.
- Utilizar branches temporárias para alterações experimentais.
- Utilizar worktrees para tarefas paralelas.

A estratégia deve ser compatível com o fluxo de trabalho existente do usuário.

Não force o uso de branches novas para tarefas triviais se a configuração não exigir isso.

### 5.2. Nomes de branches

Gere nomes previsíveis, legíveis e válidos.

Exemplos:

- `agent/fix-login-validation`
- `agent/add-terminal-session`
- `agent/refactor-api-client`
- `agent/test-database-service`

Implemente:

- Normalização.
- Limite de comprimento.
- Detecção de colisões.
- Identificação da tarefa.
- Configuração de prefixos.
- Tratamento de caracteres inválidos.

Não use apenas o nome da tarefa como identificador único.

### 5.3. Proteção da branch principal

Antes de modificar branches importantes:

- Verifique o estado atual.
- Verifique alterações pendentes.
- Identifique operações Git em andamento.
- Preserve as modificações do usuário.
- Evite reescrever histórico compartilhado sem autorização.
- Registre a operação.

Não presuma que a branch principal sempre se chama `main` ou `master`.

Descubra a configuração real do repositório.

## 6. WORKTREES PARA SUBAGENTS

### 6.1. Objetivo

Permitir que vários agentes trabalhem simultaneamente no mesmo repositório sem disputar o mesmo diretório de trabalho.

Exemplo:

- Agente A modifica o frontend.
- Agente B implementa uma API.
- Agente C cria testes.
- Agente D revisa a arquitetura.

Cada agente pode trabalhar em uma worktree separada quando as tarefas forem adequadas à execução paralela.

### 6.2. Criação de worktrees

Implemente um fluxo que:

1. Identifique o repositório principal.
2. Consulte o estado atual.
3. Selecione um commit base.
4. Escolha uma branch.
5. Crie a worktree.
6. Registre a associação com a tarefa.
7. Configure o ambiente de execução.
8. Confirme que o workspace está pronto.

Considere dependências locais que não são versionadas, arquivos ignorados, configurações de ambiente e diretórios de build.

Não copie segredos para novas worktrees desnecessariamente.

### 6.3. Isolamento de processos

Integre as worktrees com o Módulo 06.

Cada processo iniciado para uma tarefa deve ter seu diretório de trabalho correto.

O harness deve conseguir identificar quais servidores, testes e comandos pertencem a cada tarefa.

Evite que um agente execute comandos no diretório principal por engano quando deveria trabalhar em uma worktree isolada.

### 6.4. Limpeza

Implemente um processo de finalização que verifique:

- Se existem processos ativos.
- Se há alterações não commitadas.
- Se a tarefa já foi integrada.
- Se existem commits que precisam ser preservados.
- Se há arquivos não rastreados relevantes.
- Se o workspace ainda está em uso.

Não remova automaticamente uma worktree com trabalho não integrado.

Ofereça opções para preservar, integrar ou descartar alterações conforme o estado e as permissões existentes.

Quando houver múltiplas tarefas, permita filtrar por:

- Agente.
- Tarefa.

## 8. STAGING E COMMITS

### 8.1. Staging seletivo

Permita adicionar alterações específicas ao index.

O agente deve conseguir selecionar:

- Arquivos completos.
- Arquivos específicos.
- Trechos de diff, quando suportados.
- Alterações pertencentes à tarefa atual.

Evite adicionar automaticamente todo o workspace quando houver alterações preexistentes de outros agentes ou do usuário.

### 8.2. Commits

Permita que o harness crie commits quando isso fizer parte do fluxo configurado.

Implemente:

- Mensagens descritivas.
- Identificação da tarefa.
- Validação do estado do index.
- Verificação de conflitos pendentes.
- Registro do hash do commit.
- Tratamento de hooks que falham.
- Tratamento de assinaturas ou configurações de usuário ausentes.

Não configure automaticamente nome e e-mail globais do Git sem uma solicitação apropriada.

Não crie commits vazios ou que misturem alterações alheias à tarefa sem uma justificativa explícita.

### 8.3. Commits por agente

Quando houver múltiplos agentes, permita associar commits a tarefas.

Utilize mensagens que ajudem a identificar o objetivo da mudança sem incluir dados sensíveis.

Não dependa exclusivamente do texto da mensagem para determinar quais arquivos pertencem a uma tarefa.

## 9. MERGE, REBASE E RESOLUÇÃO DE CONFLITOS

### 9.1. Detecção

Antes de integrar uma branch:

- Identifique a base.
- Compare os commits.
- Detecte arquivos conflitantes.
- Verifique mudanças recentes na branch de destino.
- Consulte as alterações relacionadas.
- Identifique os testes relevantes.

### 9.2. Estratégias de integração

Permita configurar estratégias como:

- Merge tradicional.
- Fast-forward quando possível.
- Rebase quando apropriado.
- Cherry-pick de commits específicos.
- Aplicação controlada de patches.

Não utilize rebase automaticamente em branches compartilhadas sem considerar o impacto.

Não execute `reset --hard`, `clean -fd` ou operações equivalentes para solucionar conflitos de forma automática.

### 9.3. Resolução assistida

Quando ocorrer um conflito:

1. Preserve o estado conflitante.
2. Identifique os arquivos envolvidos.
3. Apresente os trechos em conflito.
4. Consulte o histórico e os diffs de origem.
5. Utilize o Módulo 07 para entender o código afetado.
6. Solicite ao agente uma proposta de resolução.
7. Valide a proposta.
8. Execute testes pertinentes.
9. Registre o resultado.

Se a resolução automática não for confiável, mantenha o conflito explícito em vez de escolher arbitrariamente uma versão.

### 9.4. Integração após validação

Antes de finalizar a integração:

- Confirme que os testes exigidos foram executados.
- Verifique o diff resultante.
- Verifique se existem conflitos pendentes.
- Confirme que as alterações pertencem às tarefas esperadas.
- Registre o commit resultante, quando houver.

A aprovação de uma tarefa pelo subagent não deve, sozinha, comprovar que a integração foi bem-sucedida.

## 10. RECUPERAÇÃO E OPERAÇÕES REVERSÍVEIS

Implemente mecanismos para investigar e recuperar operações realizadas pelo próprio harness.

Considere:

- Identificadores de operação.
- Hashes de commits.
- Estado anterior.
- Estado posterior.
- Branches temporárias.
- Reflog.
- Stash quando apropriado.
- Patches de recuperação.
- Registro de arquivos afetados.

Antes de executar uma operação destrutiva, verifique se existem modificações que não podem ser recuperadas pelo Git.

Não considere o reflog ou o stash uma garantia absoluta de recuperação de todos os arquivos.

Arquivos não rastreados, arquivos ignorados e dados externos ao repositório exigem tratamento próprio.

Não execute operações de restauração global para desfazer uma única mudança quando houver uma alternativa localizada.

## 11. INTEGRAÇÃO COM O AGENT CORE

O Agent Core deve utilizar as operações Git através de ferramentas centrais.

Fluxo esperado:

1. Receber a tarefa.
2. Consultar o estado do repositório.
3. Identificar alterações preexistentes.
4. Selecionar a estratégia de trabalho.
5. Criar branch ou worktree quando apropriado.
6. Executar as alterações.
7. Consultar os diffs.
8. Validar o resultado.
9. Integrar as alterações conforme a configuração.
10. Registrar o resultado final.

O agente deve conseguir diferenciar:

- Alterações próprias da tarefa.
- Alterações preexistentes.
- Alterações de outros agentes.
- Alterações já integradas.
- Alterações ainda pendentes.

Não considere que todo arquivo modificado durante uma tarefa foi necessariamente modificado por ela.

Utilize o estado inicial, os diffs e os registros de operações para atribuir mudanças com maior precisão.

## 12. INTEGRAÇÃO COM SUBAGENTS E ORQUESTRADOR

O Módulo 02 deve utilizar este módulo para coordenar alterações concorrentes.

Implemente:

- Associação entre tarefa, agente, branch e worktree.
- Criação de worktrees isoladas.
- Registro de commits.
- Monitoramento de alterações.
- Detecção de arquivos compartilhados.
- Verificação de dependências entre tarefas.
- Integração sequencial quando necessário.
- Integração paralela quando for viável.
- Tratamento de conflitos.
- Recuperação de falhas.
- Limpeza controlada.

O orquestrador deve conseguir identificar tarefas que podem ser executadas paralelamente e tarefas que dependem de alterações anteriores.

Não permita que dois agentes executem operações conflitantes sobre a mesma branch sem coordenação.

Quando uma tarefa depender da saída de outra, estabeleça explicitamente a ordem de integração ou atualize a base da tarefa dependente.

## 13. FERRAMENTAS DO MÓDULO

Registre as ferramentas no sistema central do harness.

Os nomes abaixo são sugestões. Reutilize os contratos existentes quando forem equivalentes.

### Estado e histórico

- `git.get_status`
- `git.get_diff`
- `git.get_file_diff`
- `git.get_history`
- `git.get_branches`
- `git.get_worktrees`
- `git.get_conflicts`

### Branches e commits

- `git.create_branch`
- `git.switch_branch`
- `git.delete_branch`
- `git.stage_changes`
- `git.unstage_changes`
- `git.commit`
- `git.compare_branches`
- `git.compare_commits`

### Worktrees

- `git.create_worktree`
- `git.get_worktree_status`
- `git.list_worktrees`
- `git.finalize_worktree`
- `git.remove_worktree`

### Integração

- `git.merge`
- `git.rebase`
- `git.cherry_pick`
- `git.resolve_conflict`
- `git.validate_integration`
- `git.get_integration_result`

### Recuperação

- `git.get_operation_history`
- `git.create_recovery_point`
- `git.restore_operation`
- `git.abort_operation`

Cada ferramenta deve possuir:

- Entrada estruturada.
- Validação de parâmetros.
- Identificação do repositório.
- Identificação da tarefa.
- Resultado estruturado.
- Tratamento de erros.
- Registro da operação.
- Verificação do estado do repositório antes e depois.

Operações destrutivas devem passar pelas regras de autorização existentes no harness.

Não exponha uma ferramenta chamada `restore_operation` que prometa recuperar qualquer estado sem verificar se os dados necessários ainda existem.

## 14. INTEGRAÇÃO COM O MÓDULO 07

Utilize o Code Intelligence para melhorar a precisão do gerenciamento Git.

Exemplos:

- Identificar os símbolos afetados por um diff.
- Encontrar arquivos relacionados a uma mudança.
- Avaliar alterações de interfaces públicas.
- Identificar testes potencialmente afetados.
- Detectar alterações semanticamente conflitantes.
- Validar renomeações.
- Comparar a estrutura do código antes e depois da integração.

Quando possível, combine a análise textual do Git com a análise sintática e semântica do Módulo 07.

Não substitua o diff real do Git por uma interpretação produzida pelo modelo.

O diff do Git deve permanecer a referência para as alterações efetivamente registradas no repositório.

## 15. INTEGRAÇÃO COM O MÓDULO 06

Execute as operações Git pelo executor central de processos quando essa abordagem for adequada.

Implemente:

- Captura de stdout e stderr.
- Códigos de saída.
- Timeouts.
- Cancelamento.
- Logs.
- Associação entre processo e tarefa.
- Tratamento de comandos que exigem interação.

Evite executar Git por strings de shell construídas sem validação.

Prefira argumentos estruturados e tratamento explícito de caminhos, opções e referências.

Quando um processo Git falhar, preserve o diagnóstico real e informe o estado da operação.

Não repita automaticamente operações de integração cujo resultado seja incerto sem verificar primeiro o estado do repositório.

## 16. TESTES AUTOMATIZADOS

Utilize o framework de testes existente.

Crie repositórios temporários e isolados para os testes. Não utilize o repositório real do usuário como ambiente descartável.

### 16.1. Testes de estado

Verifique:

- Repositório limpo.
- Arquivo modificado.
- Arquivo adicionado.
- Arquivo removido.
- Arquivo não rastreado.
- Alterações staged.
- Alterações unstaged.
- Branches.
- Commits.
- Worktrees.
- Conflitos pendentes.

### 16.2. Testes de branches

Verifique:

- Criação.
- Colisões de nomes.
- Troca de branch.
- Branch inexistente.
- Exclusão de branch não utilizada.
- Proteção contra exclusão de branches com trabalho relevante.
- Tratamento de alterações pendentes.

### 16.3. Testes de worktrees

Verifique:

- Criação de worktree.
- Associação com a tarefa.
- Associação com a branch.
- Execução de comandos no diretório correto.
- Alterações independentes.
- Listagem.
- Finalização.
- Preservação de trabalho não integrado.
- Remoção após validação.

### 16.4. Testes de integração entre agentes

Simule dois ou mais agentes:

1. Cada agente recebe uma tarefa.
2. Cada tarefa obtém um workspace isolado.
3. Os agentes modificam arquivos.
4. O harness registra os diffs.
5. As tarefas são concluídas.
6. O orquestrador tenta integrar as alterações.
7. Os conflitos são detectados.
8. As alterações compatíveis são integradas.
9. Os resultados são verificados.

Teste tanto alterações em arquivos diferentes quanto alterações conflitantes no mesmo arquivo.

### 16.5. Testes de preservação

Crie cenários contendo alterações preexistentes do usuário.

Verifique que:

- As alterações continuam presentes.
- O staging não inclui arquivos indevidos.
- O merge não elimina modificações sem aviso.
- A limpeza não remove arquivos importantes.
- A recuperação não desfaz mudanças fora do escopo.

### 16.6. Testes de falhas

Simule:

- Merge com conflito.
- Rebase interrompido.
- Processo Git cancelado.
- Branch removida externamente.
- Worktree indisponível.
- Arquivos modificados durante uma operação.
- Falha de permissão.
- Repositório corrompido ou incompleto.
- Operação repetida.
- Desconexão entre o agente e o processo.

Verifique que o estado final seja identificado corretamente.
