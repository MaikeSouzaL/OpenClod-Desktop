# MÓDULO 03 — IMPLEMENTAÇÃO COMPLETA DE SKILLS, COMANDOS PERSONALIZADOS E HOOKS NO NOSSO AI DEVELOPMENT HARNESS

## 1. OBJETIVO PRINCIPAL

Você está trabalhando no desenvolvimento de um AI Development Harness próprio, com o objetivo de alcançar capacidades avançadas de ferramentas como Claude Code, OpenAI Codex, OpenCode, Cline, Goose e outros agentes de programação.

Sua tarefa atual é implementar, integrar e aprimorar o **Módulo 03 — Skills, Custom Commands e Hooks**.

Este módulo deve funcionar em conjunto com os módulos anteriores:

- **Módulo 01 — Agent Core:** execução central do agente, interação com modelos, ferramentas, contexto, erros e conclusão de tarefas.
- **Módulo 02 — Subagents e Orchestration:** delegação de tarefas, agentes especializados, execução paralela e consolidação de resultados.
- **Módulo 03 — Skills, Custom Commands e Hooks:** habilidades reutilizáveis, comandos personalizados, instruções contextuais e automações acionadas por eventos.

Não construa um aplicativo isolado ou uma demonstração. Implemente as capacidades no projeto existente, respeitando sua arquitetura, sua interface, seu sistema de configuração e os contratos dos módulos anteriores.

O resultado deve ser um sistema real, funcional, testável, extensível e preparado para receber novos módulos.

## 2. REGRA FUNDAMENTAL: ANALISAR, CLONAR, COMPARAR E IMPLEMENTAR

Antes de modificar qualquer arquivo:

1. Examine a estrutura completa do projeto atual.
2. Identifique a linguagem, o framework, os módulos, as interfaces, os contratos e os sistemas de configuração existentes.
3. Identifique o que já existe de skills, comandos, instruções, eventos, extensões, automações e carregamento de arquivos.
4. Execute os testes existentes e registre o estado inicial.
5. Identifique funcionalidades já implementadas que não podem ser quebradas.
6. Crie uma estratégia de integração compatível com o código existente.

Em seguida, clone os repositórios indicados neste documento para um diretório temporário de análise, fora da árvore de produção do harness.

Não quero apenas uma pesquisa, uma lista de recomendações ou um documento de arquitetura. Quero que você examine os códigos-fonte e implemente as melhorias concretas no projeto.

Para cada repositório:

- Examine o README e a documentação técnica.
- Analise os arquivos de implementação relevantes.
- Identifique a arquitetura, os formatos de configuração, os contratos e os mecanismos reutilizáveis.
- Compare a implementação encontrada com a implementação do nosso harness.
- Reutilize ou adapte a abordagem que for tecnicamente superior e compatível.
- Implemente as funcionalidades ausentes.
- Aprimore as funcionalidades existentes quando a implementação externa oferecer vantagens reais.
- Evite duplicar sistemas que já funcionam adequadamente.
- Preserve as convenções e os contratos existentes.
- Respeite as licenças dos projetos e suas obrigações de atribuição.
- Não copie cegamente dependências, arquivos ou arquiteturas incompatíveis.

Se um repositório estiver indisponível, tiver mudado de endereço ou não possuir o código esperado, registre isso e continue com as demais fontes. Não invente resultados de análise.

## 4. ARQUITETURA DO MÓDULO

Implemente o módulo utilizando os componentes equivalentes abaixo. Se o projeto já possuir componentes semelhantes, amplie-os em vez de criar duplicatas.

### 4.1. Skill Registry

Registro central de habilidades disponíveis.

Responsabilidades:

- Registrar skills internas e externas.
- Identificar skills pelo nome e identificador.
- Armazenar metadados.
- Detectar duplicidades.
- Identificar conflitos de nomes.
- Controlar versões quando necessário.
- Manter informações sobre origem e localização.
- Expor uma API para consulta das skills disponíveis.
- Permitir atualização do registro.
- Identificar skills desativadas, inválidas ou incompatíveis.

O registro deve separar a descoberta de uma skill de sua execução.

### 4.2. Skill Loader

Responsável por carregar as definições das habilidades.

Deve:

- Localizar os diretórios configurados.
- Reconhecer os formatos suportados.
- Ler metadados e instruções.
- Validar arquivos obrigatórios.
- Detectar arquivos ausentes ou malformados.
- Carregar recursos auxiliares sob demanda.
- Informar erros com detalhes suficientes para diagnóstico.
- Evitar carregar indiscriminadamente todos os arquivos de todas as skills no contexto do modelo.

Quando possível, utilize carregamento progressivo: metadados primeiro, instruções completas quando a skill for necessária e recursos adicionais somente quando solicitados.

### 4.3. Skill Resolver

Componente que identifica as habilidades adequadas para uma tarefa.

Deve considerar:

- Pedido do usuário.
- Linguagem de programação.
- Tipo de projeto.
- Arquivos relevantes.
- Framework utilizado.
- Instruções do repositório.
- Skills explicitamente solicitadas.
- Capacidades disponíveis no Agent Core.
- Disponibilidade de ferramentas necessárias.
- Restrições de contexto e orçamento de tokens.

O resolvedor deve fornecer justificativas estruturadas para a seleção, permitindo diagnosticar por que determinada habilidade foi escolhida.

A decisão do modelo pode ajudar a selecionar skills, mas não deve substituir a validação determinística de arquivos, capacidades, permissões e compatibilidade.

### 4.4. Skill Runtime

Responsável por disponibilizar e executar o procedimento definido por uma skill.

Deve:

- Carregar as instruções selecionadas.
- Disponibilizar os recursos necessários.
- Integrar a skill ao contexto da tarefa.
- Reutilizar o Agent Core para chamadas ao modelo.
- Reutilizar o registro e o executor de ferramentas existentes.
- Registrar eventos e resultados.
- Detectar falhas de carregamento.
- Permitir cancelamento.
- Evitar iniciar um segundo ciclo de agente independente quando o Agent Core já puder executar a tarefa.

Uma skill baseada em instruções não deve ser tratada automaticamente como código executável.

Quando uma skill precisar executar scripts ou comandos, utilize os mecanismos de execução já existentes, respeitando suas políticas de autorização.

### 4.5. Command Registry

Registro central de comandos personalizados.

Responsabilidades:

- Descobrir comandos disponíveis.
- Registrar nomes e aliases.
- Interpretar argumentos.
- Validar parâmetros.
- Detectar conflitos de nomes.
- Disponibilizar descrições para a interface.
- Resolver comandos para suas implementações.
- Registrar erros de execução.
- Permitir a inclusão de novos comandos sem modificar o núcleo do agente.

Os comandos devem ser integrados ao sistema de ferramentas e ao Agent Core quando fizerem sentido, evitando criar um executor paralelo desnecessário.

### 4.6. Hook Registry e Hook Dispatcher

Sistema central para registrar e despachar hooks relacionados ao ciclo de vida do agente.

Responsabilidades:

- Registrar hooks.
- Associar hooks a eventos.
- Ordenar sua execução quando necessário.
- Validar configurações.
- Aplicar limites de execução.
- Registrar resultados e falhas.
- Diferenciar hooks informativos de hooks que podem alterar uma decisão.
- Integrar os hooks ao fluxo real de execução.

Um hook deve ser uma funcionalidade efetivamente conectada aos eventos do agente, não apenas uma função registrada que nunca é chamada.

### 4.7. Instruction Resolver

Componente responsável por descobrir e combinar instruções de diferentes níveis.

Deve resolver instruções globais, de usuário, de workspace, de projeto e de diretórios, conforme o formato e as convenções adotadas pelo projeto.

Deve:

- Identificar os arquivos aplicáveis.
- Determinar a precedência.
- Preservar a origem de cada instrução.
- Evitar duplicação desnecessária.
- Detectar instruções incompatíveis.
- Aplicar limites de tamanho.
- Permitir inspeção das instruções efetivamente carregadas.
- Atualizar o contexto quando arquivos relevantes forem modificados.

Não assuma que todos os formatos externos utilizam a mesma hierarquia. Documente e implemente as regras de precedência adotadas pelo nosso harness.

## 5. SISTEMA DE SKILLS

Implemente um formato de skills documentado, simples de criar e suficientemente flexível para evoluir.

### 5.1. Estrutura sugerida

Adapte a estrutura à tecnologia do projeto:

```text
skills/
  code-review/
    SKILL.md
    references/
      review-checklist.md
    templates/
      review-report.md
    scripts/
      validate.sh

  debugging/
    SKILL.md
    references/
      debugging-guide.md

  testing/
    SKILL.md
    templates/
      test-plan.md
```

Essa estrutura é uma referência, não uma exigência para reorganizar diretórios já existentes.

### 5.2. Metadados

Cada skill deve poder declarar, conforme o formato escolhido:

- Nome.
- Identificador.
- Descrição.
- Versão opcional.
- Categorias.
- Linguagens e frameworks compatíveis.
- Requisitos.
- Ferramentas necessárias.
- Arquivos auxiliares.
- Parâmetros opcionais.
- Origem.
- Estado de disponibilidade.

Os metadados devem ser validados antes de a skill ser disponibilizada ao agente.

Não obrigue todos os campos a existir se isso impedir a compatibilidade com formatos públicos que não os exigem.

### 5.3. Descoberta de skills

O sistema deve procurar skills nos locais configurados, por exemplo:

- Diretório de skills da aplicação.
- Diretório global do usuário.
- Diretório do workspace.
- Diretórios específicos do projeto.
- Diretórios locais de extensões, caso já existam.
- Diretórios de skills explicitamente adicionados pelo usuário.

A precedência e o tratamento de nomes duplicados devem ser explícitos e testados.

Não invente caminhos específicos do sistema operacional antes de inspecionar a arquitetura atual. Forneça caminhos padrão adequados ao sistema utilizado e permita configurá-los.

### 5.4. Ativação automática e manual

Implemente dois modos:

**Ativação manual**

O usuário solicita explicitamente uma habilidade ou utiliza um comando que a ativa.

**Ativação contextual**

O agente identifica que uma skill pode ajudar na tarefa, consulta o registro e carrega suas instruções quando necessário.

A ativação contextual deve evitar carregar todas as skills indiscriminadamente. O agente deve conseguir descobrir habilidades relevantes sem consumir o contexto inteiro.

Quando uma skill for obrigatória por configuração, respeite essa configuração e informe erros se ela não puder ser carregada.

### 5.5. Skills compostas

Permita que uma tarefa utilize mais de uma skill quando houver benefício concreto.

Exemplo:

1. Skill de planejamento.
2. Skill especializada na tecnologia do projeto.
3. Skill de implementação.
4. Skill de testes.
5. Skill de revisão.

A composição deve ser coordenada pelo Agent Core e, quando apropriado, pelo orquestrador do Módulo 02.

Evite carregar instruções redundantes e identifique conflitos entre procedimentos.

Não transforme automaticamente toda tarefa em uma sequência rígida de cinco etapas. A seleção deve considerar o tipo de tarefa.

### 5.6. Recursos auxiliares

Uma skill pode incluir documentação, exemplos, templates e scripts.

Implemente carregamento de recursos sob demanda, validação de caminhos e resolução relativa ao diretório da própria skill.

O sistema não deve permitir que um caminho relativo malicioso escape do diretório autorizado sem uma validação explícita de acesso.

### 5.7. Instalação, atualização e remoção

Quando compatível com o projeto, implemente:

- Instalação de skills locais.
- Importação de diretórios existentes.
- Validação antes da ativação.
- Atualização controlada.
- Desativação.
- Remoção de skills instaladas pelo sistema.
- Detecção de alterações.
- Registro de origem e versão.
- Relatório de erros de instalação.

Não apague arquivos de projetos do usuário nem sobrescreva uma skill existente silenciosamente.

Se uma instalação exigir rede, apresente a origem e permita que a operação seja autorizada conforme a política existente. Não execute automaticamente scripts recebidos de fontes externas durante a instalação.

## 6. SISTEMA DE COMANDOS PERSONALIZADOS

O usuário deve poder criar comandos que representem tarefas recorrentes.

Exemplos:

- `/review`: revisar alterações de código.
- `/test`: identificar e executar os testes adequados.
- `/explain`: explicar um trecho de código.
- `/refactor`: planejar e realizar uma refatoração.
- `/debug`: investigar um erro.
- `/plan`: criar um plano de implementação.
- `/docs`: atualizar documentação.
- `/commit`: preparar uma mensagem de commit e, quando autorizado, executar a operação.
- `/skill`: listar ou ativar habilidades.
- `/hooks`: inspecionar hooks registrados, quando autorizado.
- `/agents`: listar agentes especializados disponíveis.

Esses nomes são exemplos. Antes de criar comandos novos, verifique quais já existem no harness.

### 6.1. Definição de comandos

Permita que comandos sejam definidos em arquivos de configuração ou formatos textuais simples.

Uma definição deve poder conter:

- Nome.
- Descrição.
- Alias.
- Argumentos.
- Instruções.
- Skill associada.
- Ferramentas necessárias.
- Parâmetros padrão.
- Política de execução.
- Diretório de trabalho.
- Opções de interação com o usuário.

Use o mecanismo de configuração que melhor se encaixe no projeto. Evite introduzir formatos incompatíveis sem necessidade.

### 6.2. Parsing de argumentos

Implemente parsing robusto para:

- Comandos sem argumentos.
- Argumentos posicionais.
- Argumentos nomeados, quando suportados.
- Texto livre.
- Caminhos com espaços.
- Caracteres especiais.
- Parâmetros ausentes.
- Valores inválidos.
- Aliases.
- Comandos desconhecidos.

Não use substituições frágeis de strings para montar comandos de shell.

Argumentos devem ser transmitidos por interfaces estruturadas sempre que possível, especialmente quando forem usados para executar processos.

### 6.3. Comandos internos e externos

Diferencie:

**Comandos internos:** operam sobre o próprio harness, consultam sessões, ativam skills, exibem configurações ou controlam tarefas.

**Comandos orientados ao agente:** enviam instruções ao Agent Core e permitem utilizar ferramentas autorizadas.

**Comandos executáveis:** iniciam programas ou scripts externos, quando isso fizer parte das capacidades existentes.

Cada categoria deve utilizar o executor correspondente. Não conceda automaticamente às definições textuais de comandos acesso irrestrito ao sistema operacional.

### 6.4. Escopo e precedência

Permita organizar comandos por escopo:

- Global.
- Usuário.
- Workspace.
- Projeto.
- Extensão.

Defina precedência, detecção de colisões e mecanismos de desambiguação.

Não permita que um comando de um projeto substitua silenciosamente um comando privilegiado do sistema.

### 6.5. Experiência na interface

Integre os comandos à interface existente.

Quando aplicável, implemente:

- Autocompletar nomes.
- Exibição da descrição.
- Sugestões de argumentos.
- Indicação de comandos indisponíveis.
- Mensagens de erro compreensíveis.
- Histórico de comandos.
- Feedback de execução.
- Indicação de tarefas em andamento.
- Cancelamento de tarefas compatíveis.

Não crie uma segunda interface de chat se o harness já possuir uma.

## 7. SISTEMA DE HOOKS DO CICLO DE VIDA

Implemente hooks reais e conectados aos eventos internos.

Os nomes a seguir são uma proposta de contrato. Adapte-os aos nomes e padrões da arquitetura existente.

### 7.1. Eventos de sessão

- `session.created`
- `session.resumed`
- `session.before_close`
- `session.closed`

### 7.2. Eventos de solicitação

- `request.received`
- `request.before_process`
- `request.after_process`

### 7.3. Eventos de contexto

- `context.before_build`
- `context.after_build`
- `context.before_compaction`
- `context.after_compaction`

### 7.4. Eventos do modelo

- `model.before_call`
- `model.after_call`
- `model.call_failed`

### 7.5. Eventos de skills e comandos

- `skill.discovered`
- `skill.before_load`
- `skill.after_load`
- `skill.before_activate`
- `skill.after_activate`
- `command.before_execute`
- `command.after_execute`
- `command.failed`

### 7.6. Eventos de ferramentas

- `tool.before_execute`
- `tool.after_execute`
- `tool.execution_failed`
- `tool.approval_required`

### 7.7. Eventos de execução

- `task.started`
- `task.progress`
- `task.before_complete`
- `task.completed`
- `task.failed`
- `task.cancelled`

Não implemente eventos sem conectá-los aos pontos corretos do fluxo de execução.

### 7.8. Contrato de um hook

Cada hook deve poder definir:

- Identificador.
- Nome.
- Eventos associados.
- Ordem ou prioridade.
- Condições de ativação.
- Escopo.
- Tipo de ação.
- Tempo limite.
- Política de falha.
- Estado habilitado/desabilitado.
- Origem.
- Metadados de diagnóstico.

O dispatcher deve fornecer um contexto estruturado contendo somente as informações necessárias ao evento.

### 7.9. Tipos de hook

Implemente tipos distintos, de acordo com as necessidades do projeto:

**Observação:** recebe informações e registra métricas ou logs, sem modificar o fluxo.

**Transformação:** pode modificar dados explicitamente autorizados, como contexto ou parâmetros validados.

**Validação:** verifica uma condição e devolve um resultado estruturado.

**Controle de fluxo:** pode permitir, bloquear ou solicitar intervenção humana nos pontos em que o contrato permite isso.

**Execução externa:** inicia uma ferramenta ou processo através do executor existente, quando permitido.

Não permita que um hook de observação altere silenciosamente parâmetros, decisões ou resultados.

### 7.10. Ordem e concorrência

Defina regras claras para execução:

- Hooks sequenciais quando a ordem for relevante.
- Hooks paralelos quando forem independentes e seguros.
- Limites de concorrência.
- Timeout individual.
- Cancelamento.
- Tratamento de falhas.
- Evitar chamadas recursivas acidentais.
- Evitar execução duplicada do mesmo hook para o mesmo evento.

A falha de um hook informativo não deve necessariamente interromper uma tarefa. A falha de um hook obrigatório de validação pode impedir a operação, conforme sua política configurada.

### 7.11. Configuração de hooks

Permita ativar, desativar e configurar hooks.

Registre claramente quais hooks estão habilitados, quais eventos recebem e qual política de falha utilizam.

Quando um hook executar comandos externos, registre a operação e aplique as regras de autorização existentes.

## 8. INSTRUÇÕES DO PROJETO E ARQUIVOS AGENTS.md

Implemente um carregador de instruções que permita ao agente compreender as regras do repositório antes de editar arquivos.

### 8.1. Descoberta

Localize os arquivos de instruções relevantes no workspace e nos diretórios que fazem parte da tarefa.

Inclua suporte a AGENTS.md e preserve compatibilidade com formatos existentes no harness.

### 8.2. Hierarquia

Defina uma política documentada para:

- Instruções globais.
- Instruções do usuário.
- Instruções do projeto.
- Instruções de subdiretórios.
- Instruções de ferramentas e skills.

Resolva conflitos de maneira previsível. Não presuma que a ordem de leitura é suficiente para resolver toda contradição.

### 8.3. Escopo por diretório

Quando o agente trabalhar em um arquivo específico, identifique as instruções aplicáveis ao caminho desse arquivo.

Evite aplicar instruções de diretórios não relacionados indiscriminadamente.

### 8.4. Cache e atualização

Implemente cache de instruções quando necessário, com invalidação ao detectar mudanças nos arquivos.

Se o projeto já tiver um mecanismo de observação de arquivos, reutilize-o.

### 8.5. Inspeção

Forneça uma maneira de diagnosticar:

- Quais arquivos foram encontrados.
- Quais arquivos foram carregados.
- Quais instruções foram aplicadas.
- Qual é a precedência.
- Quais arquivos apresentaram erros.
- Quais instruções foram excluídas por limites de contexto.

Não exponha informações privadas de outros projetos ou diretórios fora do escopo autorizado.

## 9. INTEGRAÇÃO COM O AGENT CORE E OS SUBAGENTS

Este módulo não pode funcionar como uma arquitetura isolada.

### 9.1. Integração com o Módulo 01

O Agent Core deve conseguir:

- Consultar skills disponíveis.
- Selecionar skills relevantes.
- Carregar instruções.
- Executar comandos orientados ao agente.
- Despachar hooks nos eventos adequados.
- Registrar as skills utilizadas.
- Cancelar execuções compatíveis.
- Relatar falhas de skills e hooks.

- Validação de metadados.
- Detecção de definições duplicadas.
- Separação entre instruções e código executável.
- Verificação de permissões antes de executar ferramentas.
- Aprovação para operações sensíveis quando exigida pela política do harness.
- Registro de comandos externos.
- Proteção contra execução acidental durante a instalação.
- Limites de tempo e recursos.
- Tratamento de conteúdo malformado.
- Controle de origem das skills.
- Prevenção de vazamento de segredos em logs e resultados.
