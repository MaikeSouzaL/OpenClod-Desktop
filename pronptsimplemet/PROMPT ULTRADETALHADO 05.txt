# MÓDULO 05 — BROWSER AUTOMATION AVANÇADA PARA O NOSSO AI DEVELOPMENT HARNESS

## 1. MISSÃO PRINCIPAL

Implemente no nosso AI Development Harness um sistema completo de automação de navegadores, permitindo que os agentes de IA controlem navegadores reais, naveguem por sites, interajam com páginas web, preencham formulários, gerenciem abas, acompanhem mudanças de estado e executem tarefas web de várias etapas.

O sistema deve aproveitar os recursos já implementados nos módulos anteriores:

- **Módulo 01 — Agent Core:** execução das tarefas, chamadas aos modelos, ferramentas, contexto, erros e recuperação.
- **Módulo 02 — Subagents e Orchestration:** delegação de tarefas e coordenação entre agentes.
- **Módulo 03 — Skills, Commands e Hooks:** habilidades, comandos personalizados, instruções e eventos.
- **Módulo 04 — Computer Use:** controle do desktop, mouse, teclado, screenshots e automação visual.

O Módulo 05 deverá acrescentar uma camada especializada em navegadores. Ele não deve substituir os módulos anteriores nem criar outro agente central.

O resultado deve permitir solicitações como:

- Abrir um site e navegar até uma página específica.
- Pesquisar informações em páginas públicas.
- Preencher formulários.
- Trabalhar com várias abas.
- Interagir com menus, botões, campos e tabelas.
- Esperar que páginas carreguem e que elementos apareçam.
- Consultar informações estruturadas da página.
- Capturar screenshots.
- Realizar operações repetitivas em sites.
- Trabalhar com aplicações web que utilizem JavaScript intensivamente.
- Diagnosticar erros de navegação e interação.
- Utilizar sessões de navegador persistentes, quando configuradas.
- Executar testes de interfaces web.
- Integrar a navegação com tarefas de programação e desenvolvimento.

**Não construa apenas um script de Selenium ou Playwright.** Implemente uma camada de Browser Automation reutilizável, orientada a ferramentas estruturadas e integrada à arquitetura do harness.

## 4. ARQUITETURA DO BROWSER AUTOMATION

Implemente os componentes seguintes ou aprimore os equivalentes já existentes.

### 4.1. Browser Manager

Responsável pelo ciclo de vida dos navegadores.

Deve permitir:

- Inicializar o navegador.
- Conectar a uma instância existente quando suportado.
- Identificar navegadores disponíveis.
- Criar sessões.
- Criar contextos isolados.
- Gerenciar páginas.
- Encerrar sessões.
- Consultar o estado da sessão.
- Recuperar-se de falhas.
- Reutilizar sessões quando configurado.
- Impedir que tarefas diferentes compartilhem acidentalmente um contexto privado.

O navegador pode ser gerenciado pelo próprio harness ou conectado a uma instância compatível já aberta.

Documente as diferenças entre os modos disponíveis.

### 4.2. Browser Session Manager

Implemente um gerenciador de sessões que permita:

- Criar sessões temporárias.
- Manter sessões persistentes quando configurado.
- Identificar a sessão associada a uma tarefa.
- Isolar cookies e armazenamento entre contextos.
- Gerenciar autenticação sem expor credenciais.
- Recuperar sessões quando possível.
- Encerrar sessões explicitamente.
- Detectar contextos inválidos.
- Gerenciar timeouts.

Não misture automaticamente sessões pessoais do usuário com sessões isoladas do agente.

Quando for necessário conectar-se a um navegador existente, utilize um mecanismo explícito de conexão e informe suas limitações.

### 4.3. Tab Manager

Responsável pelo gerenciamento das abas.

Deve permitir:

- Listar abas.
- Abrir uma aba.
- Selecionar uma aba.
- Fechar uma aba.
- Navegar para uma URL.
- Consultar o título.
- Consultar a URL atual.
- Esperar pela criação de uma aba.
- Detectar navegações que abrem novas páginas.
- Identificar redirecionamentos.
- Alternar entre páginas.
- Atribuir identificadores estáveis dentro da sessão.

Não utilize o índice da aba como único identificador persistente, porque a ordem pode mudar.

### 4.4. Navigation Controller

Responsável pela navegação.

Deve suportar:

- Abrir URLs.
- Navegar para trás e para frente.
- Atualizar páginas.
- Aguardar carregamento.
- Esperar por elementos específicos.
- Detectar redirecionamentos.
- Tratar falhas de DNS e conexão.
- Detectar timeouts.
- Identificar páginas de erro.
- Verificar o destino final.
- Aplicar políticas de navegação existentes.

Diferencie os estados de navegação:

- Navegação iniciada.
- Documento carregado.
- DOM disponível.
- Aplicação em execução.
- Elemento desejado disponível.
- Navegação concluída.
- Navegação malsucedida.

Não considere que a página está pronta apenas porque o evento de carregamento inicial ocorreu.

### 4.5. DOM Inspector

Implemente um componente para consultar a estrutura da página.

Deve conseguir, conforme as capacidades do navegador:

- Consultar a estrutura DOM.
- Localizar elementos.
- Ler textos.
- Consultar atributos relevantes.
- Identificar links.
- Identificar botões.
- Identificar campos.
- Identificar formulários.
- Consultar tabelas.
- Consultar listas.
- Identificar elementos visíveis.
- Detectar elementos desabilitados.
- Consultar relações entre elementos.
- Identificar iframes.
- Detectar elementos que ainda não estão disponíveis.

Não envie indiscriminadamente todo o DOM ao modelo.

Implemente consultas seletivas, limites de tamanho e representações estruturadas para reduzir o consumo de contexto.

### 4.6. Accessibility Inspector

Quando possível, utilize a árvore de acessibilidade para localizar elementos por propriedades semânticas.

Permita consultas por:

- Papel.
- Nome acessível.
- Texto.
- Estado.
- Relação com outros elementos.
- Tipo de controle.

Exemplos de alvos:

- Botão com nome “Entrar”.
- Campo de texto “E-mail”.
- Caixa de seleção com uma descrição específica.
- Link com o texto “Configurações”.

Priorize os localizadores semânticos quando forem confiáveis.

Se o site não fornecer informações acessíveis suficientes, utilize DOM, seletores ou outras estratégias compatíveis.

### 4.7. Element Resolver

Implemente uma camada única para resolver os alvos de interação.

A resolução deve poder utilizar:

1. Localizadores semânticos.
2. Árvore de acessibilidade.
3. Seletores CSS.
4. Identificadores ou atributos específicos.
5. Estrutura DOM.
6. Coordenadas obtidas de uma observação recente.
7. Computer Use visual, quando necessário.

Não force todas as estratégias a seguir uma ordem fixa. A escolha deve depender do alvo, da aplicação e da disponibilidade das informações.

O resolvedor deve detectar casos em que:

- Nenhum elemento corresponde ao seletor.
- Vários elementos correspondem ao mesmo seletor.
- O elemento está oculto.
- O elemento está desabilitado.
- O elemento não pode receber interação.
- O elemento foi substituído durante uma atualização da página.

Quando houver ambiguidade, obtenha mais informações ou utilize uma estratégia alternativa antes de executar uma ação potencialmente destrutiva.

### 4.8. Browser Action Executor

Executor central das ações do navegador.

Deve:

- Receber ações estruturadas.
- Validar os argumentos.
- Identificar a sessão e a aba.
- Resolver o alvo.
- Aplicar as políticas de execução.
- Executar a ação.
- Aguardar o resultado relevante.
- Registrar evidências.
- Retornar um resultado estruturado.

Não misture o planejamento da tarefa com a implementação de baixo nível dos comandos do navegador.

### 4.9. Browser State Observer

Responsável por observar o estado atual do navegador.

Deve fornecer, conforme necessário:

- URL.
- Título.
- Estado de carregamento.
- Aba ativa.
- Elementos relevantes.
- Textos selecionados.
- Informações de acessibilidade.
- Mudanças no DOM.
- Erros de página.
- Estado de formulários.
- Screenshots.
- Metadados da sessão.

A observação deve ser seletiva e eficiente.

### 4.10. Browser Action Verifier

Responsável por verificar se as ações produziram os resultados esperados.

Exemplos:

- Confirmar que a navegação chegou ao destino correto.
- Confirmar que um formulário recebeu os dados esperados.
- Confirmar que um botão produziu uma alteração de estado.
- Confirmar que uma aba foi aberta.
- Confirmar que uma pesquisa apresentou resultados.
- Confirmar que um arquivo foi baixado.
- Confirmar que um elemento foi selecionado.

Diferencie a confirmação de que uma ação foi enviada da confirmação de que o objetivo foi alcançado.

## 7. NAVEGAÇÃO ORIENTADA POR IA

Integre o navegador ao Agent Core por meio de ferramentas estruturadas.

O ciclo esperado será:

1. O usuário solicita uma tarefa.
2. O Agent Core identifica que precisa utilizar o navegador.
3. O agente consulta o estado atual.
4. O agente determina o próximo objetivo.
5. O resolvedor identifica os elementos necessários.
6. O executor realiza a ação.
7. O observador obtém o novo estado.
8. O verificador avalia o resultado.
9. O Agent Core continua, corrige ou encerra a tarefa.

O modelo deve receber informações relevantes, não necessariamente a página inteira.

Quando o modelo aceitar imagens, permita a utilização de screenshots. Quando não aceitar, disponibilize informações estruturadas.

Não invente que um site foi consultado, que um formulário foi enviado ou que um download ocorreu sem evidências da execução.

### 7.1. Planejamento de tarefas web

Permita a decomposição de tarefas em etapas.

Exemplo:

“Pesquise uma documentação técnica, encontre a seção necessária e extraia os passos de instalação.”

O agente deve:

- Abrir a página.
- Localizar a documentação.
- Consultar o conteúdo.
- Encontrar a seção relevante.
- Extrair as informações.
- Verificar se a resposta está completa.
- Apresentar o resultado com as fontes consultadas.

O planejamento deve ser flexível e adaptado ao estado real da página.

### 7.2. Recuperação

Se uma interação falhar, o agente deve poder:

- Consultar o estado atualizado.
- Verificar se o elemento mudou.
- Refazer a busca.
- Tentar um localizador alternativo.
- Esperar por uma condição.
- Replanejar a tarefa.
- Encerrar se não for possível continuar.

Estabeleça limites de tentativas para impedir ciclos infinitos.

Suporte, conforme a arquitetura e as bibliotecas escolhidas:

- Contextos isolados.
- Cookies.
- Local storage.
- Sessões persistentes.
- Autenticação já existente.
- Expiração de sessão.
- Logout.
- Limpeza de dados.
- Separação entre workspaces.

Não extraia nem apresente cookies, tokens ou credenciais ao modelo quando não forem necessários.

Não armazene senhas em texto simples nos arquivos de configuração ou logs.

Se for necessário utilizar uma conta pessoal, permita que o usuário autentique a sessão pelo mecanismo apropriado. Não tente contornar CAPTCHA, autenticação multifator, controles de acesso ou desafios de segurança.

Quando uma página exigir intervenção humana, informe o estado e permita que o usuário conclua a etapa necessária.

## 9. DOWNLOADS E UPLOADS

Implemente mecanismos confiáveis para lidar com arquivos.

### Downloads

- Detectar o início de um download.
- Aguardar sua conclusão.
