# MÓDULO 04 — COMPUTER USE, VISÃO COMPUTACIONAL E AUTOMAÇÃO DESKTOP PARA WINDOWS

## 1. MISSÃO

Implemente no nosso AI Development Harness um sistema completo de Computer Use que permita ao agente de inteligência artificial interagir com o computador Windows como um operador digital.

O sistema deve permitir que o agente:

- Observe a tela do computador.
- Capture screenshots e analise o conteúdo visual.
- Identifique janelas, controles, botões, campos de texto, menus e diálogos.
- Utilize informações de acessibilidade do Windows quando disponíveis.
- Mova o cursor do mouse.
- Clique, clique duas vezes, pressione e solte botões.
- Digite textos e utilize atalhos de teclado.
- Role páginas e listas.
- Alterne entre janelas e aplicativos.
- Abra e manipule programas.
- Interaja com navegadores, editores de código, exploradores de arquivos e outros aplicativos compatíveis.
- Execute tarefas compostas por várias ações.
- Observe o resultado de cada ação.
- Detecte falhas e tente estratégias alternativas.
- Interrompa uma tarefa quando necessário.
- Retome tarefas quando o estado puder ser recuperado.
- Integre a automação ao Agent Core e aos subagents já existentes.

**Não construa apenas um programa de controle de mouse.** Construa uma camada de Computer Use que possa ser utilizada pelo agente central e por outros módulos do harness.

O objetivo é permitir tarefas reais, como:

1. Abrir o Visual Studio Code.
2. Abrir um projeto.
3. Navegar entre arquivos.
4. Editar código usando os mecanismos apropriados.
5. Executar comandos no terminal integrado.
6. Observar os resultados.
7. Corrigir erros.
8. Executar testes.
9. Confirmar visualmente ou por dados estruturados que a tarefa foi concluída.

A mesma arquitetura deve permitir outros fluxos de trabalho, como utilizar aplicativos desktop, navegar em sites e preencher interfaces gráficas.

## 2. REGRA DE IMPLEMENTAÇÃO

Antes de alterar o projeto:

1. Inspecione o harness existente.
2. Identifique a linguagem, o framework, a arquitetura de execução e os sistemas de ferramentas.
3. Verifique se já existem recursos de screenshots, mouse, teclado, navegador, terminal, automação ou visão computacional.
4. Execute os testes existentes e registre os resultados.
5. Identifique o sistema operacional e as dependências realmente disponíveis.
6. Preserve o código funcional e as alterações locais do usuário.

Em seguida, clone e examine os repositórios deste documento.

Não quero apenas pesquisa ou recomendações. Quero que você utilize os códigos-fonte como referência para implementar as capacidades no harness.

Para cada projeto externo:

- Clone o repositório.
- Examine a implementação, não apenas o README.
- Identifique as bibliotecas, APIs, abstrações e algoritmos relevantes.
- Compare-os com os componentes existentes.
- Reaproveite ou adapte implementações que tragam benefícios concretos.
- Implemente funcionalidades ausentes.
- Preserve componentes próprios que já funcionam bem.
- Evite duplicar sistemas equivalentes.
- Respeite as licenças e as obrigações de atribuição.
- Registre os componentes efetivamente aproveitados.

Não substitua a arquitetura existente por um projeto externo completo sem demonstrar que isso é necessário.

## 4. ARQUITETURA DO COMPUTER USE

Implemente os componentes abaixo ou aprimore os equivalentes já existentes.

### 4.1. Computer Use Controller

Controlador central da automação.

Responsabilidades:

- Receber solicitações de ação.
- Validar os parâmetros.
- Selecionar o mecanismo de execução.
- Executar a ação.
- Registrar o resultado.
- Solicitar uma nova observação quando necessário.
- Informar falhas ao Agent Core.
- Suportar cancelamento.
- Coordenar ações sequenciais.
- Impedir que dois agentes controlem o mesmo desktop de forma conflitante.

O controlador não deve depender diretamente de um modelo específico.

### 4.2. Screen Capture Service

Responsável por capturar a tela e fornecer informações visuais ao agente.

Deve oferecer:

- Captura de todos os monitores.
- Captura de um monitor específico.
- Captura de uma região.
- Identificação da resolução.
- Informações sobre escala e densidade de pixels quando disponíveis.
- Registro temporal da captura.
- Conversão para formatos aceitos pelo modelo.
- Redimensionamento controlado.
- Compressão quando necessária.
- Cache limitado de capturas.
- Liberação de memória.
- Tratamento de erros.

Evite capturar a tela continuamente sem necessidade. Prefira capturas acionadas por eventos ou pela necessidade de observar o resultado de uma ação.

### 4.3. Window Manager

Responsável por descobrir e gerenciar janelas.

Deve permitir:

- Listar janelas disponíveis.
- Obter títulos.
- Identificar processos associados quando permitido.
- Localizar uma janela por critérios estruturados.
- Consultar a janela ativa.
- Ativar uma janela.
- Verificar se uma janela está visível.
- Detectar diálogos.
- Esperar que uma janela apareça.
- Identificar mudanças de foco.
- Distinguir a janela principal de janelas auxiliares.

Evite encerrar processos ou fechar aplicativos como consequência automática de uma falha de identificação.

### 4.4. UI Automation Service

Camada para consultar a árvore de acessibilidade e os controles do Windows.

Quando suportado, permita:

- Listar elementos.
- Consultar nomes e tipos.
- Obter identificadores acessíveis.
- Ler propriedades disponíveis.
- Consultar retângulos delimitadores.
- Descobrir relações entre elementos.
- Consultar estados habilitado/desabilitado.
- Identificar elementos focáveis.
- Consultar padrões de controle.
- Executar ações suportadas pelos próprios controles.

A estrutura de dados retornada deve ser normalizada para que o agente não dependa de uma biblioteca específica.

Quando o elemento não puder ser encontrado pela automação de interface, o sistema deve poder recorrer a estratégias visuais.

### 4.5. Input Controller

Responsável por mouse e teclado.

Deve disponibilizar operações estruturadas para:

- Mover o mouse.
- Clicar.
- Clicar duas vezes.
- Pressionar e soltar botões.
- Manter um botão pressionado durante uma operação controlada.
- Digitar texto.
- Pressionar teclas.
- Executar combinações de teclas.
- Rolar.
- Alterar o foco quando possível.
- Consultar o estado disponível do dispositivo.

Defina uma representação normalizada de teclas e botões.

Trate corretamente teclas especiais, caracteres Unicode, layouts de teclado e diferenças entre mecanismos de automação.

Não presuma que digitar texto e simular uma sequência de teclas produzem o mesmo resultado em todos os aplicativos.

### 4.6. Visual Target Resolver

Componente responsável por identificar o alvo de uma ação.

Deve poder utilizar, em ordem apropriada:

1. Referência semântica a um elemento de acessibilidade.
2. Seletor estruturado de um aplicativo ou navegador.
3. Identificador de janela e controle.
4. Reconhecimento de texto por OCR.
5. Correspondência visual de imagens.
6. Coordenadas calculadas a partir de uma observação recente.

A ordem deve poder variar conforme o tipo de aplicação.

Quando um alvo tiver sido identificado por coordenadas, registre a captura de origem, a resolução e a região que justificaram a escolha.

Não reutilize cegamente coordenadas antigas depois de mudanças significativas na janela, na resolução ou no layout.

### 4.7. Action Verifier

Componente responsável por confirmar se uma ação produziu o resultado esperado.

Exemplos:

- Depois de abrir um aplicativo, verificar se a janela apareceu.
- Depois de clicar em um botão, verificar a mudança de estado.
- Depois de digitar texto, verificar se o campo contém o conteúdo esperado quando isso puder ser consultado.
- Depois de salvar um arquivo, verificar o resultado por um mecanismo confiável.
- Depois de navegar em uma página, verificar se a navegação foi concluída.

A verificação deve utilizar a fonte de evidência mais adequada, como estado da interface, árvore de acessibilidade, resultado de uma ferramenta ou screenshot.

Não declare uma ação bem-sucedida apenas porque o clique foi enviado.

### 4.8. Action Planner

Responsável por transformar uma tarefa em ações observáveis.

Exemplo de tarefa:

“Abra o aplicativo, encontre as configurações e altere a opção solicitada.”

Plano interno possível:

1. Identificar o aplicativo.
2. Verificar se está aberto.
3. Ativá-lo.
4. Observar o estado atual.
5. Localizar as configurações.
6. Executar uma ação.
7. Observar novamente.
8. Confirmar o resultado.
9. Prosseguir ou corrigir o plano.

O planejamento deve considerar as capacidades reais das ferramentas disponíveis e não inventar controles que não foram observados.

### 4.9. Action History e Recovery

Registre um histórico estruturado das ações.

Cada registro deve incluir, quando aplicável:

- Identificador da tarefa.
- Identificador da ação.
- Tipo de ação.
- Alvo.
- Parâmetros não sensíveis.
- Momento de execução.
- Resultado.
- Evidências de verificação.
- Erros.
- Tentativas de recuperação.
- Estado final.

Não registre senhas, tokens, dados privados de formulários ou outros conteúdos sensíveis sem necessidade.

## 6. OBSERVAÇÃO VISUAL E RACIOCÍNIO DO AGENTE

Integre a observação da tela com o modelo utilizado pelo Agent Core.

### 6.1. Modelos multimodais

Se o provedor selecionado aceitar imagens, disponibilize screenshots através do contrato existente de mensagens multimodais.

Não crie uma integração exclusiva com um único provedor.

Se o modelo não aceitar imagens, utilize estratégias alternativas compatíveis, como:

- Árvore de acessibilidade.
- OCR.
- Metadados de janelas.
- Estrutura do DOM em navegadores.
- Informações estruturadas de aplicativos.

Quando nenhuma estratégia conseguir identificar o alvo com confiabilidade suficiente, o agente deve reconhecer a limitação.

### 6.2. Coordenadas

Defina um sistema de coordenadas documentado.

Considere:

- Resolução do monitor.
- Múltiplos monitores.
- Coordenadas relativas e absolutas.
- Escala de exibição do Windows.
- Janelas redimensionadas.
- Barras de título e regiões não cliente.
- Mudanças de resolução.
- Diferenças entre a resolução original e a imagem enviada ao modelo.

Se uma screenshot for redimensionada para o modelo, implemente uma transformação correta entre as coordenadas da imagem e as coordenadas reais do desktop.

### 6.3. Confiança

Quando a identificação de um alvo for incerta, registre a origem da evidência e a confiança estimada, se o mecanismo realmente produzir essa informação.

Não invente uma pontuação de confiança baseada apenas em uma suposição do modelo.

Para ações que dependam de identificação visual ambígua, prefira obter uma nova observação antes de agir.

### 6.4. Ciclo de observação e ação

Implemente o seguinte ciclo integrado:

1. Receber a tarefa.
2. Observar o estado atual.
3. Identificar o próximo objetivo.
4. Resolver o alvo.
5. Validar os parâmetros.
6. Executar a ação.
7. Observar o resultado.
8. Verificar se o objetivo foi atingido.
9. Atualizar o plano.
10. Repetir ou concluir.

O ciclo deve utilizar o Agent Core, suas ferramentas, seus estados, seus limites e seu mecanismo de cancelamento.

Não crie um segundo agente autônomo independente para executar esse ciclo.

## 7. ESTRATÉGIAS DIFERENTES PARA WEB E DESKTOP

Não utilize a mesma estratégia para todos os ambientes.

### 7.1. Navegadores

Quando for possível controlar o navegador por Playwright ou por uma integração equivalente:

- Utilize seletores.
- Identifique elementos pelo papel e pelo nome.
- Aguarde estados de carregamento.
- Consulte a estrutura da página.
- Valide o resultado da navegação.
- Utilize screenshots quando necessário.

Se o navegador não estiver acessível por uma API de automação, permita o uso da interface gráfica como alternativa.

### 7.2. Aplicativos Windows

Para aplicações nativas:

- Priorize UI Automation.
- Utilize seletores semânticos quando disponíveis.
- Use mouse e teclado como alternativa.
- Recorra a OCR e visão computacional quando necessário.
- Verifique mudanças de estado.
- Considere aplicativos com interfaces personalizadas.

### 7.3. Editores de código e terminais

Quando o objetivo for editar código, inspecione as capacidades existentes do harness.

Prefira ferramentas estruturadas de leitura e edição de arquivos quando forem mais confiáveis. Use a interface gráfica para tarefas que dependam efetivamente dela.

Não force a utilização do mouse para uma operação que já possa ser realizada com segurança por uma ferramenta especializada.

O Computer Use deve complementar as capacidades do harness, não substituí-las indiscriminadamente.

## 8. AUTOMAÇÃO DE TAREFAS COMPOSTAS

Permita que o agente execute tarefas com múltiplas etapas mantendo o estado e o histórico.

Implemente:

- Identificação do objetivo.
- Plano de ações.
- Estado atual da tarefa.
- Dependências entre ações.
- Resultado esperado.
- Verificação após ações relevantes.
- Recuperação de falhas.
- Limites de tentativas.
- Cancelamento.
- Relatório final.

Uma tarefa deve ser interrompida ou replanejada quando:

- O alvo não puder ser localizado.
- A interface mudar de maneira inesperada.
- Uma janela necessária estiver indisponível.
- A ação falhar.
- O resultado não puder ser confirmado.
- Um diálogo exigir uma decisão que não foi autorizada.
- O usuário cancelar a execução.

Evite repetir indefinidamente uma ação que está falhando.

## 9. INTEGRAÇÃO COM O AGENT CORE E OS SUBAGENTS

### 9.1. Agent Core

O Agent Core deve conseguir:

- Descobrir ferramentas de Computer Use.
- Consultar seus esquemas.
- Selecionar ferramentas adequadas.
- Executar ações.
- Receber resultados estruturados.
- Observar erros.
- Replanejar tarefas.
- Cancelar execuções.
- Registrar o histórico.
- Utilizar a verificação de resultados.

A autorização deve ser aplicada pelo executor real das ferramentas, e não depender exclusivamente de instruções enviadas ao modelo.

### 9.2. Subagents

Os subagents podem solicitar operações de Computer Use por meio do orquestrador, mas não devem controlar simultaneamente o mesmo desktop sem coordenação.

Implemente um mecanismo de exclusão mútua ou de agendamento para as ações que compartilham o mesmo ambiente gráfico.

Quando houver suporte a múltiplos desktops ou sessões isoladas, modele cada ambiente separadamente.

### 9.3. Eventos

Integre o módulo aos eventos existentes, adicionando os necessários, por exemplo:

- `computer.observation_started`
- `computer.observation_completed`
- `computer.action_started`
- `computer.action_completed`
- `computer.action_failed`
- `computer.verification_completed`
- `computer.recovery_started`
- `computer.task_completed`
- `computer.task_cancelled`

Não crie um sistema de eventos paralelo se o harness já tiver um dispatcher central.
