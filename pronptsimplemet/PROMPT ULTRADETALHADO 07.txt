# MÓDULO 07 — CODE INTELLIGENCE, ANÁLISE ESTÁTICA E MANIPULAÇÃO INTELIGENTE DE REPOSITÓRIOS

## 1. MISSÃO PRINCIPAL

Implemente no nosso AI Development Harness um sistema avançado de compreensão, navegação, análise e modificação de código-fonte.

O objetivo é permitir que o agente de IA trabalhe em projetos pequenos ou grandes compreendendo sua estrutura, seus símbolos, suas dependências, suas referências e as relações entre os arquivos.

O agente não deve depender exclusivamente de abrir arquivos inteiros, pesquisar palavras ou solicitar que o modelo deduza toda a arquitetura a partir de trechos isolados.

Ele deve conseguir consultar ferramentas especializadas para compreender o código antes de modificá-lo e verificar as consequências das mudanças depois de implementá-las.

O sistema deve oferecer capacidades para:

- Mapear a estrutura de um repositório.
- Identificar linguagens, frameworks e ferramentas.
- Analisar a estrutura sintática dos arquivos.
- Localizar funções, classes, métodos, interfaces, tipos e variáveis.
- Navegar até a definição de um símbolo.
- Encontrar referências e usos.
- Identificar importações e dependências.
- Construir um mapa de relações entre módulos.
- Pesquisar código com rapidez.
- Detectar erros estáticos.
- Identificar possíveis impactos de uma alteração.
- Realizar edições precisas.
- Comparar versões antes e depois da edição.
- Executar verificações de qualidade.
- Produzir informações estruturadas para o Agent Core e os subagents.

O módulo deve integrar-se aos módulos anteriores, especialmente:

- Módulo 01 — Agent Core.
- Módulo 02 — Subagents e Orchestration.
- Módulo 03 — Skills, Custom Commands e Hooks.
- Módulo 06 — Terminal, Shell e Execução de Processos.

O Módulo 05 pode ser utilizado quando o projeto de programação envolver código de aplicações web, mas não replique suas funcionalidades de automação de navegador.

**Importante:** não implemente apenas um indexador de arquivos ou um mecanismo de busca textual. Construa uma camada de inteligência sobre o código-fonte, utilizando parsers, analisadores, servidores de linguagem e ferramentas de pesquisa quando forem adequados.

## 2. REGRAS OBRIGATÓRIAS DE IMPLEMENTAÇÃO

Antes de modificar o projeto:

1. Inspecione a arquitetura atual do harness.
2. Identifique a linguagem e o framework utilizados.
3. Examine o sistema de leitura e edição de arquivos.
4. Verifique se já existem ferramentas de busca, indexação ou análise de código.
5. Examine a integração com o terminal do Módulo 06.
6. Verifique como o Agent Core registra e executa ferramentas.
7. Execute os testes existentes.
8. Identifique os componentes que podem ser reutilizados.

Em seguida, clone e examine os repositórios indicados neste documento.

Para cada repositório, identifique os componentes relevantes e compare suas implementações com o harness existente.

Implemente as melhorias diretamente no projeto.

Não entregue apenas uma pesquisa, uma lista de bibliotecas ou um documento de arquitetura. O resultado esperado é código funcional, integrado e testado.

Não substitua componentes existentes que já funcionam sem demonstrar uma vantagem técnica concreta.

Não crie uma segunda infraestrutura de execução de ferramentas quando o Agent Core já oferecer uma.

Não presuma que o harness foi desenvolvido em TypeScript, Python, Rust ou qualquer outra linguagem. Escolha as integrações conforme a arquitetura real encontrada.

## 4. ARQUITETURA DO MÓDULO

Implemente os componentes a seguir ou amplie os equivalentes existentes.

### 4.1. Repository Analyzer

Responsável por descobrir e caracterizar o projeto.

Deve identificar:

- Raiz do repositório.
- Estrutura de diretórios.
- Arquivos de configuração.
- Linguagens predominantes.
- Frameworks identificáveis.
- Sistemas de build.
- Gerenciadores de pacotes.
- Testes.
- Linters.
- Configurações de compilação.
- Arquivos de instrução para agentes.
- Estado do Git.

O analisador deve construir um mapa inicial do projeto sem ler indiscriminadamente todos os arquivos em sua totalidade.

Deve respeitar arquivos ignorados, diretórios gerados e arquivos binários.

### 4.2. Language Detection Service

Implemente detecção de linguagem com base em evidências como:

- Extensão.
- Conteúdo.
- Configuração do projeto.
- Manifestos.
- Gramáticas disponíveis.
- Servidores de linguagem instalados.

Permita que diferentes linguagens coexistam no mesmo repositório.

Não classifique todo um projeto pela extensão de apenas um arquivo.

### 4.3. Symbol Index

Construa um índice de símbolos.

Sempre que possível, registre:

- Nome.
- Tipo de símbolo.
- Linguagem.
- Arquivo.
- Linha e coluna.
- Escopo.
- Assinatura.
- Visibilidade.
- Símbolo pai.
- Relações com outros símbolos.
- Origem da informação.
- Confiança ou limitações da análise.

O índice deve distinguir símbolos encontrados por análise sintática de informações obtidas por análise semântica.

### 4.4. Dependency Graph

Construa um grafo de relações entre arquivos, módulos e símbolos.

Considere:

- Importações.
- Exportações.
- Chamadas.
- Herança.
- Implementação de interfaces.
- Referências.
- Dependências entre pacotes.
- Relações entre testes e código de produção.

Cada relação deve registrar sua origem e, quando possível, sua localização.

Não invente dependências que não tenham sido identificadas.

Quando uma relação for apenas estimada, deixe isso explícito.

### 4.5. Code Search Service

Implemente uma camada de pesquisa que selecione a estratégia apropriada para cada consulta.

Estratégias possíveis:

- Pesquisa textual.
- Expressões regulares.
- Pesquisa por símbolo.
- Pesquisa estrutural.
- Navegação semântica via LSP.
- Pesquisa de referências.
- Pesquisa de diagnósticos.

O agente deve poder combinar resultados quando necessário.

### 4.6. Language Server Manager

Crie um gerenciador de servidores de linguagem.

Deve ser responsável por:

- Descobrir servidores instalados.
- Iniciar servidores.
- Configurar o workspace.
- Negociar capacidades.
- Enviar solicitações.
- Receber respostas.
- Gerenciar notificações.
- Manter o estado do documento.
- Detectar desconexões.
- Reiniciar servidores quando necessário.
- Encerrar servidores.
- Controlar recursos.

Não inicie um servidor novo a cada consulta se uma instância válida puder ser reutilizada.

Mantenha servidores separados quando a configuração do projeto exigir ambientes distintos.

### 4.7. Diagnostics Manager

Centralize diagnósticos provenientes de:

- Parsers.
- Servidores LSP.
- Compiladores.
- Linters.
- Ferramentas de análise estática.
- Testes.

Cada diagnóstico deve conter, quando disponível:

- Arquivo.
- Intervalo de linhas e colunas.
- Severidade.
- Código.
- Mensagem.
- Ferramenta de origem.
- Possível correção.
- Estado atual.
- Relação com alterações recentes.

Não apresente avisos, erros sintáticos e falhas de testes como se fossem a mesma categoria.

### 4.8. Code Change Impact Analyzer

Antes de uma alteração relevante, o agente deve conseguir identificar os componentes potencialmente afetados.

Considere:

- Referências diretas.
- Importações.
- Interfaces públicas.
- Assinaturas.
- Tipos compartilhados.
- Testes relacionados.
- Arquivos de configuração.
- Dependências conhecidas.

A análise não precisa garantir que todas as consequências sejam descobertas, mas deve separar dependências confirmadas de hipóteses.

### 4.9. Code Editing Engine

Centralize as alterações de código em um serviço capaz de:

- Ler o trecho relevante.
- Identificar o contexto.
- Aplicar uma alteração.
- Verificar se o conteúdo original ainda corresponde ao esperado.
- Detectar conflitos.
- Preservar codificação e finais de linha.
- Gerar diffs.
- Validar o resultado.
- Reverter uma alteração quando necessário.

Reutilize o mecanismo de edição existente no harness se ele já atender aos requisitos.

Não crie um editor alternativo sem necessidade.

## 7. PRECISÃO DA ANÁLISE

Diferencie explicitamente três níveis de compreensão.

### Nível 1 — Pesquisa textual

Baseada em texto, nomes e padrões.

É rápida, mas pode encontrar falsos positivos e não resolve necessariamente símbolos homônimos.

### Nível 2 — Análise sintática

Baseada em árvores sintáticas e parsers.

Consegue identificar estruturas do código, mas não garante resolução semântica completa.

### Nível 3 — Análise semântica

Baseada em compiladores, índices semânticos ou servidores de linguagem.

Pode resolver tipos, símbolos e referências com maior precisão, dependendo da linguagem e da configuração.

O harness deve informar qual método produziu cada resultado.

Quando o método semântico não estiver disponível, utilize alternativas compatíveis e indique suas limitações.

Não afirme que um símbolo é uma referência confirmada se a ferramenta apenas encontrou uma correspondência textual.

## 8. EDIÇÃO PRECISA E PROTEÇÃO CONTRA REGRESSÕES

### 8.1. Alterações localizadas

Antes de editar um arquivo:

1. Leia a região relevante.
2. Identifique o símbolo ou trecho alvo.
3. Verifique se o conteúdo corresponde ao esperado.
4. Aplique a alteração.
5. Gere um diff.
6. Confirme que a alteração ocorreu no local correto.

Evite substituir um arquivo inteiro quando uma alteração localizada for suficiente.

### 8.2. Controle de conflitos

Se o arquivo mudar entre a leitura e a edição:

- Detecte a mudança.
- Não sobrescreva silenciosamente o conteúdo novo.
- Releia a região afetada.
- Recalcule a alteração.
- Preserve modificações de outros agentes.

Utilize hashes, versões ou mecanismos equivalentes para detectar conteúdo desatualizado.

### 8.3. Renomeação de símbolos

Quando houver suporte semântico, implemente renomeações que considerem referências válidas ao símbolo.

Não use substituição textual global como substituto de uma renomeação semântica.

Antes de aplicar uma renomeação em vários arquivos:

- Consulte o servidor ou mecanismo responsável.
- Examine o conjunto de alterações.
- Verifique conflitos.
- Apresente ou registre o diff.
- Aplique as mudanças de forma coordenada.
- Valide os resultados.

### 8.4. Preservação de alterações existentes

O repositório pode conter modificações feitas pelo usuário antes da tarefa.

Não descarte essas mudanças.

Antes de aplicar operações em lote, examine o estado do Git e mantenha as alterações fora do escopo intactas.

Não execute comandos destrutivos de restauração apenas para limpar o workspace.

### 8.5. Validação pós-edição

Depois de uma mudança relevante, execute as verificações apropriadas:

- Parsing.
- Diagnósticos.
- Lint.
- Verificação de tipos.
- Compilação.
- Testes.
- Comparação do diff.

Selecione as verificações de acordo com a tecnologia e a magnitude da alteração.

Não execute toda a suíte de testes em cada pequena edição se houver uma estratégia incremental mais adequada.

1. Receber a solicitação.
2. Identificar o repositório.
3. Consultar a estrutura do projeto.
4. Localizar os símbolos relevantes.
5. Identificar arquivos relacionados.
6. Consultar referências e dependências.
7. Planejar as alterações.
8. Aplicar as mudanças.
9. Consultar os diagnósticos.
10. Executar verificações pelo Módulo 06.
11. Corrigir erros encontrados.
12. Produzir um resumo baseado nos resultados reais.

A análise deve ser orientada pela tarefa.

Não indexe ou envie todo o repositório ao modelo sem necessidade.

Utilize consultas estruturadas para fornecer somente o contexto relevante.

## 10. INTEGRAÇÃO COM SUBAGENTS

Os subagents devem compartilhar a infraestrutura de inteligência de código.

Exemplos:

- Agente arquiteto consulta dependências e interfaces.
- Agente de frontend localiza componentes e seus usos.
- Agente de backend encontra rotas, serviços e modelos.
- Agente de banco identifica consultas e camadas de persistência.
- Agente de testes localiza testes relacionados.
- Agente de revisão consulta diffs e referências.
- Agente de debugging examina diagnósticos e fluxos de chamadas.
